## Observed hot spots (notes for the optimization pass — observations only, no code changed)

1. **Eager boot construction in `apps/api/src/index.ts`.** Before
   listen, boot constructs dozens of stores/services, each opening
   its own SQLite file in the data dir (governance, billing cost +
   spend caps, checkpoints, dots, recordings, chat queue, peer
   approvals, widgets, credential proposals, spans, run-health,
   health-sync, tiered memory, and more), plus seed loading and
   per-bot overlay passes (policies, personas, avatars, workspaces,
   models, voice, skills, approval modes, layers, memory settings,
   imported bots, chief overlays). Deferring rarely-used stores
   behind lazy access is the obvious first cold-start lever.
2. **`ToolSpillStore.read()` (and the newer `search()`) re-read
   the whole spilled file on every call**
   (`packages/agent-runtime/src/tool-spill.ts`: `readFileSync`
   of the full file, then slice/scan). A multi-MB spill paged in
   8 KB chunks re-reads the entire file per chunk.
3. **Source maps + type declarations ship in `apps/api/dist`.**
   The per-extension table above shows how much of the dist total
   is `.map` (source maps) and `.ts` (declaration files, counted
   by final extension) rather than runnable `.js`.
4. **Web export duplication.** `apps/web/out` contains both an
   `.html` and a `.txt` payload per page plus the `_next`
   chunk tree; worth checking whether the `.txt` payloads are
   needed by the serving path before shipping both.
5. **MCP warmup is (correctly) after listen**, so it does not block
   cold start — but it runs during the idle window measured above,
   so idle RSS/CPU in the first minute includes connector warmup
   activity, not just steady-state idling.
6. **Background timers start at boot** (e.g. the 60 s
   credential-proposal expiry sweep, checkpoint-retention timers).
   Individually cheap; collectively they define the idle wakeup
   floor.

## Pack B optimization pass — before / after (2026-11-02)

The table above is the AFTER run (warm compile cache — see below). The
baseline below was measured with this same script earlier the same day,
on the same machine (Node v24.22.1, linux/x64), BEFORE the optimization
pass. Changes shipped in the pass:

1. **Node module compile cache** — `apps/api/src/index.ts` calls
   `enableCompileCache()` as its first executable step (guarded). The
   static import graph is already loaded by then, but the dozens of
   route/service modules `boot()` pulls via dynamic `import()` are
   parsed on every boot without it. Repeat boots skip that parse work.
2. **Span-store retention** — `SpanStore.pruneOldRuns()` (defaults:
   ended runs older than 30 days, cap 20,000 ended runs; env overrides
   `KRIYADOT_SPAN_RETENTION_DAYS` / `KRIYADOT_SPAN_MAX_RUNS`), swept
   daily from API boot. The observability DB previously grew without
   bound; this bounds long-term disk growth (a long-horizon win — it
   does not move the 60-second numbers below).
3. **Spill content cache** — `ToolSpillStore` caches decoded handle
   content (LRU, 32 MB cap; spill files are write-once per id). Paging
   or searching one large handle no longer re-reads/re-decodes the
   whole file per call.

| Metric | Baseline | After (cold compile cache) | After (warm compile cache) |
| --- | ---: | ---: | ---: |
| Server cold start (spawn → /api/health) | 2,391 ms | 3,520 ms | **1,170 ms** |
| Idle RSS at +60s (main process) | 281 MB | 245.7 MB | 253.7 MB |
| apps/api/dist total | 11,397.9 KB | — | 11,523.9 KB |
| apps/web/out total | 5,940.7 KB | — | 5,956.9 KB |

Read the cold-start row honestly:

- **Repeat boots are the product case** (a desktop app launched daily):
  2,391 → 1,170 ms, **−51%**.
- The cold-cache run is a first-ever boot with an empty compile-cache
  directory: it PAYS a one-time cache-write cost (and cold page cache on
  freshly built files) and lands slower than baseline. That cost is
  paid once per code version, not per boot.
- Idle RSS improved ~10–13% (281 → 246–254 MB); the two after-runs
  differ by ~8 MB between themselves, so treat the exact figure as
  ±10 MB run variance, not a precise constant.
- Dist sizes grew slightly (+126 KB api, +16 KB web) — that is the
  weight of the Pack A features themselves (model-auto, ingestion,
  citations, memory explorer), not optimization slippage. The ~4.2 MB
  of `.map` files exist only in the dev dist; the shipped single binary
  is Bun-compiled from TypeScript source and never includes them.

What was deliberately NOT done: deferring/lazifying the ~250 store and
route constructions in `apps/api/src/index.ts` (a 5,570-line boot file)
was measured to sit behind module loading as the smaller half of boot,
and restructuring it risks the whole surface for a projected gain the
compile cache already captures more safely. The Bun single-binary path
is unaffected by the compile cache (it ahead-of-time bundles); these
numbers describe the Node entry (`apps/api/dist/index.js`), which is
also what the desktop shell's dev/self-host modes run.
