# KriyaDot — Final QA Report (2026-10-30)

**Scope of this pass:** the full post-build QA phase ordered after the
OMB+Octop build, the Octomind 100% closure build, the Lightning cloud layer,
and the keyless free-LLM stack — tree at GitHub main `33ebc2c7` (CI green)
plus the fixes made during this pass. Six parallel workstreams (core E2E,
federation/care/email/purchasing, cloud/phone/install, failure modes,
security red team, platform/CI/docs) plus coordinator-run integration,
fix verification, and live re-verification.

**Verdict: PASS WITH TWO DOCUMENTED OPEN ITEMS.** Every test suite is green
(5,427 tests, up from the 5,410 baseline — 17 new regression tests), the
root build passes, and every live end-to-end flow in scope was exercised
against the real assembled server. Twelve defects were found and fixed,
including one Critical that broke the product's primary flow. Two issues
are documented open rather than fixed: both are architectural, both are
bounded by the shipped trust model, and both are written up with repros
and recommended fixes in §9. A list of things no test on this machine can
establish is in §10 — this report does not claim zero problems on hardware,
accounts, or platforms it cannot touch.

**Method constraints (as ordered):** no paid APIs, no real third-party
accounts or keys. Providers were mocks, loopback fixtures, injected
fetches, or the genuinely anonymous public lanes the product itself ships
(OVHcloud AI Endpoints anonymous tier). One real anonymous OVH catalog
check was used to verify the keyless model roster against reality.

## 5. Failure modes

- **Sandbox resolution**: with no Docker on this VM, the kernel backend
  (Landlock, ABI 8) is selected and `$HOME`//`/usr` writes are denied.
  With a stub Docker binary, the resolver selects Docker with the correct
  confinement arguments (`--network none --memory 512m --read-only
  --tmpfs`, unique container name, kill-reap). Real-Docker confinement is
  **unverifiable here** (no Docker on this VM) — see §10.
- **Landlock helper missing**: self-heals by recompiling; if unbuildable,
  degrades to host execution with a loud `sandboxed:false` (non-strict) or
  fails closed with an error (strict policy). **PASS**
- **Malformed MCP server**: a garbage server fails connect in ~490 ms with
  a health error and reason; a server that elicits then dies fails the
  tool call in ~264 ms — no hangs. **PASS**
- **Provider dying mid-turn**: a mid-turn hard quota death fires an honest
  failover event and the turn completes on the backup; a plain 500 does
  not fail over mid-turn (by design) but health-based failover engages on
  turn 4 after 3 failures; a mid-stream socket drop yields partial tokens
  then an honest error. **PASS** — plus QA-D04/QA-D05 (§8) for the
  silent-endpoint hang and the retried hard-quota 429 found here.
- **Disk/temp exhaustion** (`ulimit -f`): writes fail with a clean
  `error: disk I/O error`; the server stays healthy. **PASS**
- **Plugin crash/hang**: invoke-level isolation held (crash → ~84 ms
  `PluginRpcError`; hang → ~807 ms timeout and the child is SIGKILLed).
  The aggregate `PluginManager.tools()` listing lacked the same isolation
  — **FIXED** (QA-D11, §8).

## 6. Security / red team

Attempted live bypasses against booted instances; results stated as
observed.

**Held:**
- Governance: 16 direct catastrophic command forms denied, including
  `python -c os.system('rm -rf /')` and quoted/chained variants.
  Indirect wrapper forms (script file, `$CMD`, base64, curl-pipe)
  classify as require-approval — the gateway sees only wrapper text; a
  human approval gate still applies. Design residual, documented.
- Approval forgery/replay: replay → 409 in all four attempts; missing or
  wrong token → 401.
- SSO tokens on the general API: 401 — the SSO and API auth systems are
  disjoint; an SSO token does not silently gain admin. **Held as
  documented.**
- Federation: replayed envelope → 401 `replay`; wrong-key signature → 401;
  tampered timestamp → 401.
- Plugins: traversal zip → 400 before approval with zero escaped writes;
  child environment is scrubbed (child env = `[PATH, PLUGIN_DIR,
  PLUGIN_ID]`; a decoy secret was absent).
- Pages XSS battery (published and preview): payloads appear only
  entity-escaped under a strict CSP. **Held.**
- Secrets sweep: zero decoy-key hits across server logs, databases, and
  API responses from the E2E runs.
- Purchase policy: hard blocks and the approval requirement held at the
  executor (and see QA-D06 for the policy-write side door, now closed).

**Not held / open:** tenancy `x-user-id` spoof (OPEN-1) and plugin child
processes not fs/network sandboxed (OPEN-2) — §9.

**Code-level observations (not separately exploitable as shipped):**
`POST /api/terminal/sessions/:id/input` writes raw keystrokes with no
governance evaluation — it sits behind loopback auth and is the owner's
own shell by design. `GET /api/auth/bootstrap` returns the loopback token
when Origin is absent/allowlisted — the loopback trust boundary the TUI
relies on. Prompt-injection and MCP Apps bridge checks were code-reviewed
only: the test instances had no LLM provider configured for a live
injection turn (see §10).

## 8. Defects found and fixed

Severity scale: Critical = primary flow broken; High = feature broken or
security-relevant bypass in a realistic configuration; Medium = security
weakening or broken secondary path; Low = polish/correctness nit.

### QA-D01 — CRITICAL — every HTTP chat path returned 401 in the assembled server
The routes.ts chat handler re-validated **any** Bearer credential as a
companion device token, ignoring the loopback middleware's
`req.loopbackAuthed` flag — so the web UI's own loopback token got
`401 {"error":"Invalid companion device token"}`. Companion device tokens
died one layer earlier at the loopback middleware, and the companion
`/chat/send` proxy's inner fetch carried no credential and forwarded the
401. The product's primary flow was dead over HTTP while every unit suite
stayed green (unit tests mount the router without the middleware +
companion stack). **Fix (coordinator):** `loopback-auth.ts` gained
`LoopbackAuthOptions.isCompanionChatToken` (pass-through for
`POST /api/chat` only; the handler re-validates and audits);
`index.ts` wires the validator (`companionStore.findDeviceByToken`) and
passes `loopbackToken` into the router deps; `routes.ts` skips companion
validation when `req.loopbackAuthed` and forwards `localChatToken` to the
companion routes; `companion-routes.ts` sends
`Authorization: Bearer <loopbackToken>` on its proxied inner call.
**Regression test:** `apps/api/test/chat-auth-assembly.test.ts` mounts the
full assembled stack — 5/5 pass. **Live re-verified:** loopback-token chat
completes a turn (§2).

### QA-D02 — HIGH — OVH anonymous lane: a dead model killed the whole turn
The keyless driver rotated models only on 429; a 404 threw and killed the
turn. Worse, roster model `Qwen3-32B` is **genuinely absent** from the live
anonymous catalog (verified 2026-10-30 against the anonymous
`GET /v1/models`: 22 models; gpt-oss-120b and Meta-Llama-3_3-70B-Instruct
present; Qwen3-class present as Qwen3.5-9B, Qwen3.6-27B, Qwen3.8-27B,
Qwen3.5-397B-A17B). **Fix** (`packages/agent-runtime/src/providers/ovh-anonymous.ts`):
rotate on 404/5xx/network errors; remember 404'd models in
`unavailableModels` and skip them unless all are dead; default per-call
timeout `OVH_DEFAULT_TIMEOUT_MS = 60_000`. Roster `Qwen3-32B` →
`Qwen3.6-27B` in `ovh-anonymous.ts`, `catalog.json`, and
`providers-closure.test.ts` expectations. **Regression tests** in
`providers-qa-regressions.test.ts`.

### QA-D03 — HIGH — zero-key first-run chat broken end-to-end
The compound effect of QA-D01 + QA-D02: with no keys configured, the
first-run promise ("chat works with zero setup") failed over HTTP.
Fixed by D01 + D02; **live re-verified** post-fix (§2): the turn completes
on the OVH lane with an honest fallback notice in-stream.

### QA-D04 — MEDIUM — no default provider timeout: silent endpoints hung turns forever
`openai-compatible.ts` applied no timeout when neither `timeoutMs` nor
`replyTimeoutMs` was set; `aihorde.ts`'s poll bound never advanced when a
single fetch hung. **Fix:** remote endpoints default to
`DEFAULT_PROVIDER_TIMEOUT_MS = 300_000`; AI Horde bounds every request
(`AIHORDE_REQUEST_TIMEOUT_MS = 30_000`, signals combined). **Refinement
during final regression:** the first version of this fix also bounded
*local* endpoints and broke the deliberate local-driver contract
(`engines-fleet` "none configured → no signal"); the default now applies
only to non-local base URLs (`isLocalBaseUrl` — localhost/127.0.0.1/::1/
0.0.0.0/*.local stay unbounded by design; factory presets for local
engines carry their own `replyTimeoutMs`). **Regression tests:**
`providers-qa-regressions.test.ts` (incl. OVH silent-endpoint timeout and
Horde silent-submit abort).

### QA-D05 — LOW — hard-quota 429 retried 4× before failover
**Fix:** `fetchWithRetry` peeks the 429 body via `res.clone()` (guarded —
test-stub Responses may lack `clone`) and skips retries when
`classifyProviderError` returns kind `limit`. **Regression tests:** quota
429 = exactly 1 attempt; transient 429 keeps bounded retries.

### QA-D06 — MEDIUM — purchase always-allow side door via policy write
`POST /bots/:id/allow-tool` refused `request_purchase`, but
`PUT /bots/:id/policy` accepted `allow ^request_purchase$` (the
validator's privileged probes omitted it) and policy/simulate then
returned allow. (A second defense held throughout: PurchaseService
requires a genuinely `approved` card before executing.) **Fix:**
`apps/api/src/bot-policies.ts` probes now include `request_purchase`,
`edit_file`, `create_file`, `remove_file`. **Regression test:**
`apps/api/test/bot-policies-purchase.test.ts` (20/20 with
`purchases.test.ts`). **Live re-verified:** the policy write now returns
400 with the privileged-tools message.

### QA-D07 — MEDIUM — FCM configured-but-broken reported a fake send
`apps/api/src/push.ts` reported `{attempted:1, sent:1}` while delivering
nothing when FCM was configured but broken. **Fix:** silent-return paths
now throw, so an undelivered push is never counted sent (probe: sent:0;
push suites 22/22).

### QA-D08 — MEDIUM — email to any IP-configured server always failed TLS
`apps/api/src/email-transport.ts` passed `servername: host`
unconditionally; Node TLS throws "Setting the TLS ServerName to an IP
address is not permitted", so mail against IP-configured SMTP/IMAP
servers could never connect. **Fix:** `isIP` SNI guard in both connect
paths. Post-fix harness 9/9 (§3).

### QA-D09 — LOW — CLI workflow run printed no run id
The CLI read `res.id`; the API returns `{ runId }`. **Fix:**
`packages/cli/src/workflow-commands.ts` reads `res.runId ?? res.id`.
**Regression test:** `packages/cli/test/workflow-run-id.test.ts` (1/1).

### QA-D10 — HIGH — Node runtime boot broken; Dockerfile deployment broken; TLS fail-open; subpath WebSockets broken
Four platform defects from one workstream:
1. `node dist/index.js` crashed on the bare lazy-`require()` idiom
   (28 files / 56 hits) while Bun booted clean — and `apps/api/Dockerfile`
   ran exactly that Node path, so Docker deployment was broken as shipped.
   **Fix:** a global `createRequire` shim installed at the top of
   `apps/api/src/index.ts` (no-op guard under Bun) — zero per-file rewrites;
   Dockerfile base bumped `node:22-slim` → `node:24-slim` in both stages
   (node:sqlite is flag-gated on 22, unflagged on 24). **Live verified:**
   `node apps/api/dist/index.js` boots and serves health 200; Bun boot
   unchanged.
2. WebSocket upgrades ignored `KRIYADOT_BASE_PATH` (upgrades bypass
   Express middleware, and the handler matched only unprefixed paths).
   **Fix:** base path hoisted to `serverBasePath` in `index.ts`; the

3. TLS misconfiguration failed open: a missing cert path silently booted

   was corrected to the real env names (TLS_CERT_PATH / TLS_KEY_PATH /
   ACME_STORE_DIR). **Live verified:** boot with a nonexistent cert
   refuses to start. `deployment-polish.test.ts` updated to the new

### QA-D11 — LOW — plugin aggregate tool listing had no per-plugin isolation
`PluginManager.tools()` let one hanging plugin break the whole aggregate

## 9. Open items (documented, not fixed in QA)

### OPEN-1 — Tenancy identity is an unauthenticated header (HIGH in a multi-user model / MEDIUM as shipped)
**Live repro:** an org created as `x-user-id: alice-wse` correctly 403s
user `bob` — until `bob` changes only the header to `alice-wse`, which
returns 200 with the full member list and allows an admin invite POST
(201, **including the invite token**); accepting that invite as a third
identity created a durable, persisted **admin** membership. Root cause:
`tenancy.ts` `callerOf()`/`roleOf()` trust the `x-user-id` header, and
the same pattern scopes identity in `brand.ts`, `cloud-routes.ts`
(per-user Lightning credentials), `composio.ts` (per-user vault),
`installations.ts`, and `kb-routes.ts`.
**Why not fixed in QA:** as shipped, every one of these routes sits
behind the single loopback owner token — the spoof does not cross the
instance trust boundary (anyone who can set the header already holds the
owner token). Binding identity properly is architectural: derive the
caller from an authenticated principal (SSO session / loopback identity),
treat `x-user-id` as a profile hint only, and gate org-admin persistence
on verified identity when SSO is configured. Ripping the header out
inside QA would break the local multi-profile UI and many suites.
**This must be fixed before any multi-user or hosted deployment.**
Note the boundary that does hold: SSO tokens return 401 on the general
API (§6) — the spoof requires the owner token, not merely an SSO login.

### OPEN-2 — Plugin child processes are not filesystem/network sandboxed (MEDIUM residual)
**Live-confirmed:** a plugin declaring `network:false, env:[]` could
still read the host's `.api-token` file and open a socket. The
`permissions.network` field is declarative only; the child runs as the
host OS user. This is documented in code and mitigated by deny-by-default
install approval, and the install UI copy was corrected during QA to stop
calling plugins "sandboxed" (QA-D12). The real fix — running plugin
children under the kernel sandbox backend — is architectural and belongs
in a feature phase, not QA.
